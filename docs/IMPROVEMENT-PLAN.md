## P0. 외부 변경이 로컬 편집을 지운다

### 문제

에디터에 입력한 내용이 아직 호스트로 전송되지 않았을 때 외부 변경이 도착하면, 외부 변경을 채택하면서 로컬 입력을 버린다.
사용자에게는 "The editor reloaded it." 알림 한 줄만 나간다. `useDocumentSync.ts`의 `consumeExternal` 주석이 이 한계를 이미 적고 있다.

이 확장은 `*.llm.md`를 연다. AI 에이전트가 파일을 고치는 동안 사람이 같은 문서를 열어 두고 편집하는 흐름에서
이 충돌이 가장 자주 난다.

### 재현

2026-09-23에 Playwright로 재현했다. 절차는 이렇다.

1. `# Title\n\nbody`를 연다.
2. 첫 문단 끝에 ` LOCAL`을 입력한다.
3. 100ms 뒤 `external_update`로 `...\n\nEXTERNAL`을 보낸다. 에디터에 포커스가 있으므로 보류된다.
4. 헤더의 Raw 버튼을 누른다.

결과: 호스트로 나간 마지막 `change`에 `EXTERNAL`은 있고 `LOCAL`은 없다. 버튼을 누를 때 난 `focusout`이 보류분을 채택했고,
그 시점에 ` LOCAL`은 디바운스(300~600ms) 안에 있어 전송되지 않은 상태였다.
Raw 버튼 대신 에디터 밖 아무 곳이나 눌러도 같은 경로를 탄다.

### 설계

채택하는 시점에 전송하지 않은 로컬 편집이 있는지를 먼저 본다.

- **없으면** 지금처럼 조용히 채택한다. 동작이 바뀌지 않는다.
- **있으면** 채택을 멈추고 에디터 위에 충돌 막대를 띄운다. 보기는 셋이다.
  - **외부 변경 채택**: 로컬 입력을 버리고 외부 내용으로 다시 그린다. 지금의 동작이다.
  - **내 편집 유지**: 로컬 전체 텍스트를 호스트로 보낸다. 외부 변경은 되살리지 않는다.
    에디터 안의 `Ctrl+Z`는 ProseMirror 실행 취소를 먼저 하므로 외부 변경을 되돌리지 못한다.
  - **차이 보기**: 외부 내용과 로컬 내용을 둘 다 읽기 전용으로 나란히 띄운다. 지금의 merge view는 Raw 모드 안에서
    git HEAD와 편집 가능한 현재 문서를 비교하므로 그대로 쓰지 않고 별도 오버레이로 둔다. P0 다음 커밋에 넣는다.

막대가 떠 있는 동안에는 보류 상태를 유지하므로 `canSend()`가 전송을 막는다. 규칙 1이 그대로 지켜진다.
`focusout`과 1.5초 타이머에 의한 자동 채택은 전송하지 않은 로컬 편집이 없을 때만 일어난다.

"전송하지 않은 로컬 편집"은 훅의 플래그 하나로 판정한다(`hasUnsentEdits()`). `postChange`나 `debouncedSerialize`를
부를 때 켜고, 실제로 `change`를 보냈거나 외부 변경을 채택했을 때만 끈다. 디바운스 대기 여부로는 판정할 수 없다.
보류 중에는 디바운스가 만료돼도 `canSend()`에 막혀 전송 없이 끝나므로, 대기 여부로 보면 편집이 없는 것처럼 보인다.

설계를 코드와 대조하면서 함께 막아야 할 경로 셋을 더 찾았다.

- **모드 전환**: `toggleMode`가 `canSend()`를 거치지 않고 `change`를 보냈다. 로컬 편집이 있으면 `focusout`이 더는
  채택하지 않으므로, 이대로 두면 Raw 버튼이 외부 변경을 조용히 덮어쓴다. 보류 중에는 전환하지 않고 전송은 `sendNow`를 거친다.
- **Raw 모드**: 보류 중 CodeMirror 입력도 1.5초 뒤에 버려졌다. Raw 모드에는 BlockNote 에디터가 없어 `buildDocumentText()`가
  null을 돌려주므로, "내 편집 유지"는 원문 텍스트(`documentText`)를 보낸다.
- **포커스 밖 외부 변경**: 에디터에 포커스가 없고 2초 넘게 입력이 없으면 `external_update`를 보류하지 않고 바로 채택했다.
  전송하지 않은 편집이 있거나 이미 보류 중이면 포커스와 무관하게 보류한다.

줄 단위 3방향 자동 병합은 이번에 넣지 않는다. 병합 결과가 틀리면 사용자가 알아채기 어렵기 때문이다.
충돌 막대를 실제로 써 보고 같은 문단을 건드리지 않는 충돌이 대부분이면 그때 다시 검토한다.

### 완료 기준

위 재현 절차를 `e2e/external-conflict.spec.ts`에 영구 테스트로 둔다.

| 경우 | 기대 |
|---|---|
| 로컬 편집 없이 외부 변경 | 막대 없이 채택되고 기존 E2E `external_update`가 통과한다 |
| 로컬 편집 후 Raw 버튼 | 막대가 뜨고 모드가 바뀌지 않으며 에디터에 `LOCAL`이 남는다 |
| 로컬 편집 후 1.5초 대기 | 막대가 뜨고 에디터에 `LOCAL`이 남는다 |
| 충돌 후 "내 편집 유지" | 마지막 `change`에 `LOCAL`이 있다 |
| 충돌 후 "외부 변경 채택" | 에디터에 `EXTERNAL`이 있고 `LOCAL`이 없으며, `LOCAL`이 담긴 `change`가 나가지 않는다 |
| 막대가 떠 있는 동안 입력 | `change`가 나가지 않는다 |
| Raw 모드에서 충돌 후 "내 편집 유지" | 마지막 `change`에 `LOCAL`이 있다 |

"외부 변경 채택"의 기대를 원안에서 바꿨다. 호스트가 이미 외부 내용을 갖고 있으므로 채택할 때는 `change`를 보내지 않는다.

진단에 `external_conflict` 이벤트를 더하고 고른 보기를 `choice` 필드로 남긴다. `docs/MONITORING.md`의 이벤트 표와
`PROBLEM_EVENTS`를 함께 고친다.

## P1. 구조와 검증

### P1-1. 전송 경로를 하나로 모은다

`App.tsx`에서 `change`를 직접 보내던 두 자리(모드 전환, blur 자동 포맷)는 P0에서 `sendNow(text)`로 옮겼다.

남은 것은 `saveToHost`다. 프론트매터 편집이 `postChange`를 부르기 전에 `lastSentTextRef`를 먼저 바꿔서,
보류 중에 전송이 막히면 보내지 않은 텍스트가 "마지막으로 보낸 텍스트"로 남는다. 이 대입을 지우고 훅의 전송 경로에 맡긴다.

**완료 기준**: `App.tsx`에서 `lastSentTextRef.current =` 대입이 0건이다. 기존 E2E와 P0 테스트가 통과한다.

## 추가 검토 1. 한 번만 편집해도 문서 전체가 다시 쓰인다

2026-09-23 정기 검토에서 더했다.

### 문제

웹뷰는 편집할 때마다 문서 전체를 BlockNote로 직렬화해서 보낸다. 호스트의 `updateTextDocument`는 앞뒤 공통 부분만 뺀 범위를 치환한다.
그래서 왕복 변환에서 원문과 달라지는 줄이 문서 앞쪽과 뒤쪽에 하나씩만 있어도 그 사이 전체가 다시 쓰인다.
한 글자를 고쳐도 git diff에 문서 대부분이 잡힌다.

달라지는 줄 가운데 일부는 표기만 바뀌지만, 일부는 문서의 뜻을 바꾼다.

### 근거

**실제 문서 모음 측정**: `D:\git` 아래 md 파일 5,350개 가운데 200KB 미만인 400개를 무작위로 뽑았다.
저장 경로(`generateMarkdownFromEditor`)와 같은 변환 체인으로 한 번 왕복시킨 뒤 `compareRoundtrip`으로 원문과 견줬다.

| 결과 | 파일 수 |
|---|---|
| 원문과 같음 | 70 |
| 달라짐 | 330 (82.5%) |
| 변환 실패 | 0 |

측정 스크립트는 BlockNote 기본 스키마를 쓴다. 앱은 mermaid와 callout 블록을 더한 스키마를 쓰므로 그 두 블록이 든 문서에서는 결과가 다를 수 있다.

**유형별 최소 재현**: 아래는 합성한 입력으로 한 번 왕복시킨 결과다. 세 번 연속 왕복시켜 같은 결과로 수렴하는지도 확인했다.

| 입력 | 결과 | 뜻이 바뀌는가 | 수렴 |
|---|---|---|---|
| `see [init.md](init.md) now` | `see init.md now` | 링크가 사라진다 | 수렴 |
| `see [https://x.io](https://x.io)` | `see https://x.io` | 링크가 자동 링크 여부에 맡겨진다 | 수렴 |
| `> A\n>\n> B` | `> A\\\n> B` | 인용 안의 두 문단이 한 문단으로 합쳐진다 | **발산**: 왕복할 때마다 `> ` 뒤 공백이 늘어난다 |
| `<div>\n  <img src="x.png"/>\n</div>` | 줄마다 끝에 `\`가 붙는다 | HTML 블록 안에 `\` 문자가 그대로 보인다 | 수렴 |
| `line one\nline two` | `line one\\\n line two` | 부드러운 줄바꿈이 강제 줄바꿈이 되고 다음 줄 앞에 공백이 생긴다 | 수렴 |

| `---` | `***` | 표기만 바뀐다 | 수렴 |
| 표 | 열 너비를 공백으로 채운다 | 표기만 바뀐다 | 수렴 |
| 언어 없는 펜스 | `` ```text ``가 붙는다 | 표기만 바뀐다 | 수렴 |
| `__b__` | `**b**` | 표기만 바뀐다 | 수렴 |

부드러운 줄바꿈을 강제 줄바꿈으로 바꾸는 것은 `preserveMarkdownLineBreaks`가 의도한 동작이다. WYSIWYG에서 원문의 줄 구분을 그대로 보이려는 것이다.
결함은 두 가지다. 다음 줄 앞에 공백이 생기는 것, 그리고 편집하지 않은 문단까지 디스크에서 바뀌는 것이다.

### 설계

두 단계로 나눈다.

**1단계: 뜻이 바뀌는 손실 넷을 개별로 고친다.** 위 표에서 뜻이 바뀌는 행이 대상이다.
하나를 고칠 때마다 `test-roundtrip.mts`에 그 입력을 넣는다.

- 텍스트와 주소가 같은 링크: 파싱 전에 보호하고 직렬화 뒤에 되살린다. `protectHtml`과 같은 방식이다.
- 인용 안의 빈 줄: 원인이 `preserveMarkdownLineBreaks`의 `isStructural`인지 BlockNote 파서인지 먼저 가른다. 발산하는 유일한 항목이라 가장 먼저 한다.
- HTML 블록의 `\`: `restoreHtml`은 주석 안의 `\`만 걷어낸다. HTML 블록 안까지 넓힌다.
- 강제 줄바꿈 뒤의 앞 공백: 직렬화 결과에서 `\\\n ` 뒤의 공백 하나를 걷어낸다. 원문에 있던 들여쓰기와 구별되는지를 테스트로 확인한다.

**2단계: 편집하지 않은 블록은 원문 조각을 그대로 쓴다.** 표기만 바뀌는 행까지 없애는 근본 해법이다.
문서를 열 때 최상위 블록마다 원문 조각을 기억해 두고, 저장할 때 내용이 그대로인 블록은 원문 조각을 내보낸다.
변경 범위가 크므로 1단계를 마친 뒤 설계를 따로 검토한다. 이번 항목의 완료 기준에는 넣지 않는다.

### 2단계 설계: 원문 조각 보존

2026-09-24에 사용자가 2단계 설계안을 먼저 기록하라고 정했다. "WYSIWYG만 남기기 위한 조건"의 첫째와 둘째 행, 그리고 추가 검토 6에서 넘어온 사례 일곱이 이 단계로 모인다.

#### 문제

지금은 한 글자만 고쳐도 문서 전체를 BlockNote로 다시 직렬화한다. 그래서 BlockNote가 원문과 다르게 쓰는 모든 줄이 함께 바뀐다.
처음 1단계 설계에서는 "최상위 블록마다 원문 조각을 기억한다"고 적었다. 그러나 블록과 원문 줄을 짝짓는 것은 어렵다.
BlockNote는 목록 항목 하나를 블록 하나로 만들고, 빈 줄 보존 문단을 끼워 넣고, 인용 안의 문단을 합친다. 블록 수와 원문의 구획 수가 맞지 않는다.

#### 설계: 블록 대신 줄 단위 3방향 병합

블록을 짝짓지 않는다. 저장할 때 세 텍스트를 줄 단위로 병합한다.

| 이름 | 무엇인가 | 언제 정하는가 |
|---|---|---|
| 원문 O | 디스크에서 읽은 본문. frontmatter는 지금처럼 따로 떼어 둔다 | 문서를 열 때, 외부 변경을 채택할 때, Raw 모드에서 WYSIWYG로 돌아올 때 |
| 기준 C | O를 파싱한 직후, 편집 없이 직렬화한 결과. 지금의 왕복 자가검증이 이미 만든다 | O와 같은 시점 |
| 편집 결과 N | 지금 에디터를 직렬화한 결과. 지금 저장하는 값이다 | 저장할 때마다 |

C에서 N으로 바뀐 줄은 사용자 편집이다. C에서 O로 바뀐 줄은 BlockNote가 원문과 다르게 쓴 서식 차이다.
diff3로 사용자 편집만 O에 적용한 결과 R을 저장한다. 두 변경이 같은 구간에 겹치면 그 구간은 N을 쓴다. 편집이 우선이고, 그 구간의 서식 차이만 잃는다.

**안전장치**: R을 다시 파싱해 직렬화한 결과가 N과 같아야 한다. 다시 열었을 때 지금 에디터와 같은 문서가 된다는 뜻이다.
같지 않으면 R을 버리고 지금처럼 N을 저장한다. 그 경우도 지금보다 나빠지지 않는다.

- **C는 두 경로에서 계산한다.** 왕복 자가검증은 에디터를 처음 만들 때만 돌고, 외부 변경을 채택해 블록을 교체하는 경로에서는 돌지 않는다. 블록을 교체한 직후 저장 체인(`serializeBlocks`)으로 C를 만들고, 자가검증도 이 C를 다시 쓴다.

**측정 중에 찾아 고친 결함**: 목록 항목 추가만 병합 성공률이 80%였다. `normalizeUnorderedListBullets`의 수평선 판정이 `* **굵게**`의 앞부분을 수평선으로 보고

## 추가 검토 3. 큰 문서를 여는 시간이 블록 수의 제곱으로 는다

2026-09-23 세 번째 정기 검토에서 더했다.

### 문제

큰 문서는 여는 데 몇 초씩 걸리고, 블록 수가 두 배가 되면 여는 시간은 두 배보다 더 늘어난다.
원인은 `@blocknote/core` 0.51.4의 공통 node view 생성 코드다. 에디터 화면을 처음 그릴 때 블록마다 node view를 만든다.
그때마다 블록 ID로 `editor.getBlock(id)`를 부르고, `getBlock`은 문서 전체를 `descendants`로 처음부터 훑어 그 ID를 찾는다.
블록이 N개면 이 탐색이 N번 돌아 전체 비용이 N²에 비례한다.

### 근거

모두 2026-09-23에 Playwright(Chromium)로 dev 서버에 대고 쟀다. 문서는 합성했다.

|---|---|---|---|
| 500 | 1,001 | 311ms | |
| 1,000 | 2,001 | 486ms | 1.6배 |
| 2,000 | 4,001 | 1,059ms | 2.2배 |
| 4,000 | 8,001 | 2,674ms | 2.5배 |

블록 수가 두 배가 될 때 배율이 1.6배에서 2.5배로 커진다. 블록 수에 비례하는 비용 위에 제곱으로 느는 비용이 얹혀 있다.

**CPU 프로파일 (헤딩, 문단, 목록, 표 1,000 단위, 12,001줄, 여는 시간 8.1초)**: 모든 프레임의 포함 시간을 모았다.

`@blocknote/core`, `@blocknote/react`, `@blocknote/mantine`을 같은 버전으로 함께 올린다.
0.55.0은 2026-09-22에 나와 하루밖에 지나지 않았으므로 0.54.2를 권한다. 리뷰할 때 정한다.

올려도 해결되지 않거나 올리는 비용이 크면, 0.51.4의 node view 생성 코드만 alias로 바꾸는 방법이 남는다. 추가 검토 2와 같은 방식이다.

### 추가 검토 7. 부분 선택을 복사하면 블록 전체가 복사된다

2026-09-24 정기 검토에서 더했다. "WYSIWYG만 남기기 위한 조건"의 셋째 행이다.

#### 문제

WYSIWYG에서 문단의 일부만 선택해 복사해도 그 문단 전체가 마크다운으로 클립보드에 들어간다.
여러 블록에 걸쳐 선택하면 첫 블록과 마지막 블록도 선택하지 않은 부분까지 통째로 들어간다.
원인은 `App.tsx`의 `onCopy`가 `editor.getSelection()`을 쓰는 데 있다. 이 API는 선택이 걸친 블록을 통째로 돌려준다.
BlockNote 0.54.2의 타입 정의가 이것을 밝히고 있다: "If the selection starts / ends halfway through a block, the returned data will contain the entire block."
같은 파일의 `getSelectionCutBlocks()`는 선택된 부분만 잘라 블록으로 돌려준다.

#### 근거

2026-09-24, Playwright Chromium, 클립보드 읽기 권한. 선택한 뒤 300ms를 기다리고 `Ctrl+C`를 눌렀다. 세 번 반복해 세 번 모두 같았다.
문서는 `# Title\n\nHello **bold** and [link](a.md) and \`code\`.\n\n- item one\n- item **two**\n\n> quote *it*`이다.
"잘라낸 블록" 열은 복사 이벤트 안에서 `getSelectionCutBlocks()`의 결과를 `blocksToMarkdownLossy`로 만든 것이다.

| 선택 | 지금 클립보드 | 잘라낸 블록 |
|---|---|---|
| 첫 문단 전체 (Home, Shift+End) | `Hello **bold** and [link](a.md) and \`code\`.` | 같다 |
| 첫 문단의 `bold and` | 첫 문단 전체 | `**bold** and` |
| 첫 문단 끝 두 글자부터 목록 끝까지 | 첫 문단 전체와 목록 | `` `e`. `` 와 목록 |
| 인용 끝 네 글자 | `> quote *it*` | `> e *it*` |

클립보드에는 앱이 쓴 `- item` 형태가 남았다. BlockNote가 먼저 `* item` 형태로 쓰고, 앱이 `await` 뒤에 덮어쓴다.
기다린 측정에서는 앱 쪽이 매번 이겼다. 다만 `blocksToMarkdownLossy`는 0.54.2에서 동기 함수(`string`을 돌려준다)이므로, `await`를 둘 이유가 없다.

측정 스크립트는 `C:\Users\Administrator\AppData\Local\Temp\claude\D--git-my-md-editor\e8e7b238-ec9a-4e03-8e37-6f6529d68193\scratchpad\zz-copy`에 있다.
`cut2.spec.ts`가 위 표를 만든다. webview 폴더에 복사한 뒤 `npx playwright test -c zz-copy/pw.config.ts zz-copy/cut2.spec.ts`로 돌린다.

#### 설계

- `onCopy`에서 `getSelection()` 대신 `getSelectionCutBlocks()`를 쓴다.
- 처리기를 동기로 바꾼다. `preventDefault`와 `setData`가 같은 이벤트 처리 안에서 일어나게 한다.
- 선택이 한 블록 안에 있으면 블록 표식(`# `, `> `, `- `)을 붙이지 않고 인라인 마크다운만 복사한다. 여러 블록에 걸치면 블록 표식을 붙인다.
  한 블록 안의 일부를 복사하는 것은 문장을 옮기려는 것이고, 표식까지 따라오면 붙여 넣은 곳의 구조가 바뀌기 때문이다.
  이 규칙은 리뷰할 때 사용자 의견을 들을 여지가 있다.
- 지금처럼 `normalizeOrderedListNumbers`, `normalizeUnorderedListBullets`, `restoreHtml`을 거친다. 저장 경로와 같은 표기가 되도록 `fromEditorMarkdown`도 거친다.
- 코드 블록 안의 선택은 지금처럼 코드 텍스트만 복사한다. 펜스로 감싸지 않는다.

같은 E2E를 세 번 연속 돌려 모두 통과한다.

#### 결과

2026-09-24에 code 세션이 설계대로 고쳤다(`8a5a25e`). 한 블록 안의 선택은 블록 표식 없이 복사하는 규칙도 그대로 넣었다.

설계에 하나를 더했다. 복사 처리기 첫머리에서 ProseMirror가 화면 선택을 즉시 읽어 들이게 한다(`view.domObserver.flush()`).

사용자가 선택하자마자 Ctrl+C를 눌러도 결과가 흔들리지 않는다. 공개되지 않은 내부 API이므로 없으면 조용히 건너뛴다.

E2E(`e2e/copy.spec.ts`)는 완료 기준의 여섯 경우에 코드 블록 경우를 더해 일곱이다. 세 번 연속 돌려 모두 통과했다.

- **선택은 DOM Range로 만든다.** 처음에는 키보드로 선택했는데, 병렬 부하에서 방향키 입력이 빠져 선택이 기대와 달랐다(`ello **bo**`, `T`).
  글자 위치를 지정해 Range를 만들고, 복사만 실제 Ctrl+C로 한다. 사용자가 마우스로 드래그해 선택한 경우와 같은 경로다.
- **클립보드는 이벤트에서 읽는다.** OS 클립보드는 병렬 워커가 함께 써서 테스트끼리 서로의 값을 읽었다. 복사 이벤트가 `window`까지 올라왔을 때 `clipboardData`를 읽는다.

### 추가 검토 8. 저장하고 다시 열면 보이는 문서가 바뀐다

2026-09-24 정기 검토에서 더했다. "WYSIWYG만 남기기 위한 조건"의 넷째 행(서식과 보기 불일치)이다.

사용자가 WYSIWYG에서 본 것이 파일에 그대로 남는지를 직접 재는 판정이다.

#### 문제

BlockNote 직렬화기가 굵게나 기울임 안의 인라인 코드를 저장할 때, 코드 뒤 조각의 여는 구분자 바로 뒤에 공백을 둔다.
CommonMark에서 여는 `**` 뒤에 공백이 오면 그 `**`는 굵게를 열지 못한다. 그래서 다시 열면 `**`가 글자 그대로 보인다.
한 번 망가지면 그 상태로 굳어 더 바뀌지 않으므로 사용자가 알아채기 전까지 남는다.

| 입력 | 처음 연 모델 | 저장 결과 | 다시 연 모델 |
|---|---|---|---|
| `**auditd \`auid=-1\` 만 기록된다**` | 굵게 `auditd `, 코드 `auid=-1`, 굵게 ` 만 기록된다` | `**auditd** \`auid=-1\`** 만 기록된다**` | 굵게 `auditd`, 평문 ` `, 코드, **평문 `** 만 기록된다**`** |
| `**굵게 \`코드\` 뒤**와 평문` | 같은 모양 | `**굵게** \`코드\`** 뒤**와 평문` | 끝 조각이 평문 `** 뒤**와 평문` |
| `*기울임 \`code\` 끝*` | 같은 모양 | `*기울임* \`code\`* 끝*` | 끝 조각이 평문 `* 끝*` |

앞 조각의 끝 공백은 BlockNote가 이미 구분자 밖으로 옮긴다(`**auditd** `). 코드 뒤 조각의 앞 공백만 옮기지 않는다.
처음 여는 단계에서도 코드 조각의 굵게는 사라진다. 모델에는 굵게 없는 코드로 담긴다. 이 항목에서는 다루지 않는다.

한국어 문서에서 흔한 다른 경계는 문제가 없었다. `이제 **중요.**다음`, `결과는 **87.5%**이다`, `**결론**: 끝`은 다시 열어도 같았다.

  **47개(11.8%)에서 다시 연 모델이 처음과 달랐다.** 변환 실패는 0이었다.

### 추가 검토 13. 앱 전처리가 인라인 코드와 같은 이름의 일반 링크를 바꾼다

2026-09-24 정기 검토에서 더했다. "남은 불일치" 2번의 남은 7개 파일을 가르다 찾았다. 이 항목은 BlockNote 한계가 아니라 **앱 자체의 결함**이다.

#### 문제

셋이다. 모두 `markdownTransforms.ts`의 위키링크와 HTML 보호 처리에서 생긴다.

1. **인라인 코드 안이 화면에서 바뀐다.** `parseWikilinks`와 `protectHtml`은 `mapOutsideCodeFences`로 코드 펜스만 피하고 인라인 코드는 피하지 않는다.
   그래서 `` `[[Note]]` ``가 에디터에서 코드 `[Note](Note.md)`로 보이고, `` `<b>x</b>` ``의 코드 텍스트에는 보이지 않는 보호 문자(U+200B)가 섞인다.
   파일은 저장할 때 되돌아오지만, 화면의 코드가 원문과 다르고, 찾기로 `<b>`를 찾으면 보호 문자 때문에 걸리지 않을 수 있다(찾기는 재지 않았다).
2. **같은 이름의 일반 링크와 코드가 위키링크로 바뀐다.** 앱은 위키링크를 "이 문서에 나온 이름 목록"(`wikilinkNames`)으로만 기억한다.
   저장할 때 `serializeWikilinks`가 목록에 있는 이름의 `[x](x.md)`를 모두 `[[x]]`로 되돌리므로, 원래 일반 링크였거나 코드 안의 글자였던 것까지 바뀐다.
3. **이름에 꺾쇠가 든 위키링크는 되돌아오지 않는다.** `` `[[misc/<slug>]]` ``는 `protectHtml`이 먼저 `<`에 보호 문자를 넣은 뒤 `parseWikilinks`가 이름을 기록한다.
   저장할 때는 `restoreHtml`이 보호 문자를 지운 다음 `serializeWikilinks`가 이름을 찾으므로 서로 맞지 않는다. 그 결과 `[misc/<slug>](misc/<slug>.md)`로 저장된다.
   원인을 코드 순서로 읽고 판단했다. 순서를 바꿔 확인하지는 않았다.

#### 설계

- **인라인 코드도 피한다.** `mapOutsideCodeFences`와 같은 방식으로 코드 펜스와 인라인 코드 스팬을 모두 피하는 함수를 두고, `parseWikilinks`, `protectHtml`, `serializeWikilinks`, `restoreHtml`이 그것을 쓴다.
  인라인 코드 스팬은 CommonMark 규칙대로 같은 개수의 백틱 짝으로 찾는다. 다른 전처리가 인라인 코드를 건드려야 하는지는 하나씩 확인한다.
- **위키링크를 이름이 아니라 자리로 기억한다.** 파싱할 때 위키링크에서 온 링크를 나타나는 순서대로 기록하고, 저장할 때 같은 순서의 링크만 되돌린다.
  편집으로 링크 수가 달라지면 이름과 순서가 모두 맞는 것만 되돌린다. 방법은 리뷰할 때 고른다. 링크 주소에 표식을 싣는 방법은 화면과 복사에 드러나므로 쓰지 않는다.
- **보호와 복원의 순서를 맞춘다.** 이름을 기록하기 전에 보호 문자를 걷어 내거나, 복원할 때 같은 순서를 쓴다. 인라인 코드를 피하게 되면 셋째 결함의 대부분이 함께 사라진다.
